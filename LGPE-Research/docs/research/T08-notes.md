# T08 — Representative texture/model exports and animation/particle limits

Evidence date: 2026-10-28 (Asia/Shanghai). Actual read-only input root is
`../1.0.2/2b7730a9e56498bbafac2002d4908c6b_NCA/1/`.
WSL does not mount X:. Tests and tools were executed through Windows Python,
with an existing WSL directory as process cwd and explicit Windows paths.
No original files were changed; every sample was SHA256 checked before/after conversion.
The five chosen samples cover BNTX, gfbmdl, gfbanm, VFXB PTCL and WEM.

## Full texture batch: first failure and format-specific retry

The first full pass catalogued all 1,344 BNTX files. It produced 819 PNGs, failed
448, and marked 77 DDS conversions `UNSUPPORTED`; the initial manifest called
those 77 multi-texture cases, a diagnosis corrected below. The 448 failures were
not BNTX parse failures. Their format counts were BC7_SRGB 305, BC7_UNORM 2,
R8_UNORM 138, and R8_G8_UNORM 3. FFmpeg's DDS decoder rejected BC7 and the
one/two-channel luminance DDS layouts generated by the pinned BNTX-Extractor.

Added a bounded direct adapter. BNTX-Extractor still parses BNTX and performs the
verified deswizzle. The adapter checks dimensions, DDS FourCC/DXGI format and exact
top-mip byte count; texture2ddecoder 1.0.6 decodes BC7 blocks to BGRA; R8 is expanded
to grayscale RGBA and R8_G8 preserves the first and second components in PNG R/G
with B zero and alpha opaque. The manifest records source format code, component
selectors, decoder, channel mapping, color space, output hash and validation. PNG
validation checks every chunk CRC and the decompressed row lengths. The 77
remaining rows were initially kept `UNSUPPORTED` because the extractor emitted
no DDS; later inspection showed they all use one single-face R16 texture. No file
extension is used as a substitute for decoding.

Ran `scripts/smoke_bntx.py` against four actual files, one for each failed format
family. All produced valid RGBA8 PNGs, and all source hashes matched before and
after. Full commands, input/output hashes and validation results are persisted in
ignored `logs/bntx-smoke.json`; the four outputs were disposable under
`work/bntx-smoke-*` and were not written into `decoded/`.
The targeted `retry-failed --domain texture --execute` processed exactly the 448
failed sources. All 448 succeeded; the manifest now has 1,247 `DECODED`, 20
`DECODED_EXISTING_VERIFIED`, 77 `UNSUPPORTED`, and zero `FAILED`. Its full CLI
result is in ignored `logs/texture-retry-run.json`; `manifests/textures.jsonl`
records per-file conversion metadata and output hashes. At this checkpoint, before
the model retry and BNK full batch, aggregate coverage was SCANNED 27,824 /
DECODED 16,131 / FAILED 6 / UNKNOWN 11,365 / PENDING 245 / UNSUPPORTED 77.
The later coverage result is recorded in `docs/research/STATUS.md`.

## Corrected R16 classification and completed BNTX batch — 2026-10-29

The 77 initial `UNSUPPORTED` rows were not multi-texture containers. Re-reading
the captured upstream parser output showed **one texture and one face in every
file**, all with format code `0x0A01`, dimensions 256×256 through 1024×1024, and
16-bit single-channel data. The first representative is
`bin/battle/waza/model/em000_ball_break01/fxmt_0_mask001_m.bntx` (708,720 bytes,
SHA256 `073b02668525a3aa62ad405b40f7009af65983d969c90ba34863bb6362d78dbf`).
The earlier error came from BNTX-Extractor v0.6 not including `0x0A01` in its
format table, then reporting no emitted DDS; the generic “one DDS” guard hid the
actual unsupported format.

Format identification is cross-referenced against the pinned Switch-Toolbox
`BNTX.cs` R16_UNORM support and the public BNTX format references that identify
`0x0A01` as R16_UNORM: [RTB BNTX QuickBMS mapping](https://github.com/RandomTBush/RTB-QuickBMS-Scripts/blob/master/Textures/Switch_BNTX.bms)
and [3DSkit BNTX format notes](https://github.com/Tyulis/3DSkit/blob/master/doc/BNTX.md).
The adapter uses BNTX-Extractor's existing parser and block-linear deswizzler,
checks the deswizzled top mip is exactly width×height×2 bytes, reads little-endian
UNORM16 red values, rounds them to 8-bit grayscale, and writes opaque RGBA PNG.
The sample's component selectors report Red/Red/Red/One. This exports mip 0 only;
it does not claim that the lower mip chain was exported.

`scripts/smoke_bntx.py` now includes a real R16 sample and cross-checks its
262,144 grayscale pixels against FFmpeg's independent rawvideo `gray16le`→`gray8`
conversion. The maximum per-pixel difference is 1/255, and PNG channel expansion
is verified as grayscale RGB with opaque alpha. The sample source hash was
unchanged; its PNG is 512×512, 115,103 bytes, SHA256
`ff92ce0a2fead6daa194afa4f9aac9e1172b41b2fb303c417fa4d3dba96c5806`. The full
five-format smoke results and exact command/output log are in
`logs/bntx-smoke.json`.

## GFBCol root-table structure and unresolved schema

The local scan contains **698** `.gfbcol` files totalling **752,028 bytes**;
the largest is 26,472 bytes. Before conversion, every file was checked against
the generic FlatBuffers root-table/vtable bounds without applying a Game Freak
schema. All **698/698** have the same valid envelope: root table at `0x10`, a
signed vtable displacement of `0x0c` to vtable `0x04`, a 12-byte vtable, a
20-byte root object, and four slot offsets `[4, 8, 12, 16]`. FlatBuffers itself
does not identify a schema in the buffer, so this establishes only a
FlatBuffers-compatible table structure, not the `.gfbcol` format or field
meanings ([format internals](https://flatbuffers.dev/internals/)).

Five real samples covering different sizes are listed in
`docs/research/source_lists/t08-gfbcol-smoke5.txt`. The initial five-source run
generated path-mirrored JSON views; the 20-source run then generated and
revalidated the bounded batch; the final `--limit 0` run processed **698/698**
sources with **698 root-table views validated, 698 semantic UNKNOWN, 0 FAILED,
0 PENDING**. Every output keeps the original path and stem and changes only
`.gfbcol` to `.json` under `decoded/1.0.2/romfs/`. `manifests/collisions.jsonl`
records the source and output SHA256, mirrored output path, validation state,
root/vtable offsets, and untyped four-byte slot prefixes. The JSON explicitly
sets `schema_status` and `slot_semantics` to `UNKNOWN`; it contains no guessed
collision names, mesh, or geometry.

The pinned Blender importer at
`Pokemon-Switch-Model-Importer-Blender@bb597581916c7407385afb5461efe4d2ae2f38f9`
uses `GFLib/Model/CollisionGroup.py` only through the `.gfbmdl` root model's
`CollisionGroups` vector (`Model.py:187–203`). Its `Bounding` member is a
24-byte inline struct. This is not a standalone `.gfbcol` reader, and the
matching slot count alone is insufficient to reuse its schema. The pinned
Switch-Toolbox checkout at
`3fcb87f1fea25ad56db139b0d9577db591f54118` likewise has no standalone GFBCol
loader; its collision-group accessor is part of the GFBMDL model reader. No
version-matched independent schema or loader was found, so **all 698 sources
remain high-level `UNKNOWN`** even though their generic root-table structure is
now indexed as JSON.

exclusive-create cleanup, unsafe catalog-path accounting, and a receipt-order
interruption case. The batch now resolves the decoded root and every selected
output before touching it, rejects a decoded root or mapped output that
resolves through a symlink/junction, and rejects selected absolute, drive-

results while continuing with other selected rows. Output rollback after an

created by this invocation; an exclusive-create loser leaves the other
writer's file untouched.

the next run re-decodes the source in memory, validates the existing output,
checks exact byte identity, and repairs the receipt before recording
`DECODED_EXISTING_VERIFIED`. A mismatching or structurally invalid existing
output remains a failure; it is never overwritten.
