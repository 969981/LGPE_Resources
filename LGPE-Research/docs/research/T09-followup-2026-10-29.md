# T09 follow-up — unmatched external WEM IDs

## Scope and method

This follow-up checked whether the seven loose WEM IDs absent from the current
static event graph were referenced by any of the 265 parsed banks' DIDX tables,
or were exact-byte duplicates of one of the extracted internal media members.
It also independently re-decoded three of those real loose WEM files. All source
paths below are relative to the extracted LGPE 1.0.2 RomFS; the original files
were only read.

The repository's `.venv` was not a usable WSL environment (`uv run` reported
that it had no Python executable). The CLI was run in a fresh temporary uv
environment instead, without changing the repository environment:

```sh
UV_PROJECT_ENVIRONMENT=/tmp/lgpe-t09-followup-venv uv run lgpe map-audio-events
```

The real BNK/XML and WEM receipts were revalidated. Result: `ANALYZED`, 265/265
banks parsed, 0 failures, 2,476 events, 2,552 event/action rows, 2,251 distinct
event-to-loose-WEM path pairs, 1,190 same-bank reachable-media-to-DIDX joins,
1,109/1,109 internal DIDX members reached, and 0 unverified BNK source hashes.
The mapper reported wwiser commit
`08e937b649bc7007c234bbd59e34a41d5eef3b38`; event names remain unknown because
`wwnames.db3` is absent.

The seven IDs were computed as the loose audio manifest's decimal filename
stems minus every `mediaReferences[*].sourceId` in the regenerated
`manifests/wwise_event_media.jsonl`. None of the seven numeric IDs occurs in
the 1,109-row `manifests/bnk_media.jsonl` DIDX index. None of their exact source
SHA-256 values occurs among the extracted internal WEM member hashes either.
This rules out a direct same-ID DIDX match or a byte-identical internal member
within the banks processed here. It does **not** prove the loose files are
unused or identify another runtime loading path.
